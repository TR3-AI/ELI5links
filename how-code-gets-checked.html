How your code gets checked 🔄

start to finish, step by step

On your machine · every save

Step 1 💾

You save the code

A watcher runs quietly in the background, watching your folder. The moment a file is saved, it wakes up.

⬇️
Step 2 ⏳

It waits a beat

About half a second, so a burst of saves counts as one. It ignores noise like .git and build folders.

⬇️
Step 3 🧱

Does it build?

It runs the real build on the newest code. Won't compile = red, with the file and line. (If the build fails, it stops here.)

⬇️
Step 4 ✅

Do the tests pass?

Then it runs your real tests. A failed test = red. A crash names the exact test; a freeze trips a timer.

⬇️
Step 5 🧾

It writes an honest receipt

Marks the result pass / fail / can't-tell — never a fake green, never blank when something broke.

⬇️
Step 6 🤖

It hands the result to the AI

The finding goes straight to the coding AI; if it's red, it keeps nudging until green. Save again mid-check and the old one is dropped, restarting on the newest.

When you ship

Step 7 🚦

You push or open a pull request

A soft gate on your machine checks: green? clean? nothing protected touched? If red, it blocks — a local warning you could override.

⬇️
Step 8 🔒

The cloud gate — can't be skipped

R1 (no AI): re-runs the locked tests, checks nobody weakened them, runs clippy + fmt. Then R2 (AI judge, only if R1 passed): reads the change against the plan — is it actually right? Its key stays in the cloud.

⬇️
Step 9 👀

Greptile reviews it

The pull-request reviewer reads the change and scores it out of 5.

⬇️
Step 10 🫵

You merge

Nothing reaches main without your yes. You have the last word.

🔄

The whole loop

save → build → test → honest receipt → to the AI → soft gate → cloud gate (R1 → R2) → Greptile → your merge. The compiler and tests are the judges; the gate makes “green” mean more; you sign off.
