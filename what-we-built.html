What we've actually built 🧱

every real part in the DMS repo, and how it connects

1 🧠

The Manager — the brain

The thing you talk to on Prime SKILL.md · manager/PROMPT.md · WORKFLOW.md · config.yml. It drives everything and checks the work, but never builds itself — it hands each step to the right teammate.

⬇️
2 🛤️

The planning pipeline

Turns your idea into a plan, in a fixed order. draft-one.sh merges two blind drafts → launch-first-goal.sh (Plannotator) → launch-wayfinder.sh → final goal → PRD. dispatch.sh won't let building start until the final plan is approved.

⬇️
3 🗄️

Teams and their memory

new-team-memory.sh gives a team its own private notebook — 10 seats, each with its own records (changelog, knowledge, state…). upgrade-team.sh updates an old team. The Manager writes to it with record-change / remember.

⬇️
4 📥

Getting the rules into every pane

sync-global-rules.sh pulls the one shared rulebook; pane-inject.sh loads it plus each role's prompt into its pane (latest rules first). comms.py makes sure a message hits exactly one pane and never bleeds into another team's tab.

⬇️
5 🔀

The Operations Manager

The switchboard while teams build. ops-manager.sh creates it the moment a team exists. ops-clock.sh fires timed report nudges (status, pre-block, end-of-block) and the refresh that pushes new rules to every team.

⬇️
6 🧩

Departments → one codebase

Big plans split into departments templates/department/ · DEPARTMENTS.md, each on its own branch, reassembling dept → central staging → main. dept-close.sh closes a finished team's panes but keeps its branch + history.

⬇️
7 🧪

The tested core underneath

A small Python package delegation_manager (ops, comms, memory, CLI) holds the real logic, with 120 checks passing across 11 test suites. install.sh sets it up; doctor.sh health-checks it.

The flow: Manager → plan → team + memory → rules loaded into panes → Ops runs the day-to-day → departments reassemble into one codebase — all on a tested Python core.
