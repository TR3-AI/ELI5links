① Where agents work

📁

One shared folder, or one per task?

What a "folder" is: a copy of the code, parked on one branch. Git's rule: one folder shows one branch at a time — you can't work two tasks in the same folder at once. Your 3 build agents work a task in turn: write the failing test → make it pass → tidy up, passing the same code along.

Built = one shared folder per department. All 3 agents work in ../typeless-api-integration/, parked on feat/typeless/api-001. Tidy done → switch that folder to feat/typeless/api-002 → repeat. Handing off = zero copying (same files). Cost: tasks go one at a time inside a department.

Spec = a folder per task. worktrees/…/api-001, …/api-002, …/api-003 all open at once. Cost: each agent needs its own copy and must keep syncing ("I don't see your test yet"), plus lots of folders to track and clean up.

The real question: do you want tasks running in parallel inside one department? (You already run 3 whole departments at once, either way.)

I'd: keep the shared folder — the loop is sequential by nature. Add per-task folders later only if one department turns into a bottleneck.

② Where departments join up

🔀

Straight into staging, or an extra branch first?

The setup: finished work lands on staging, where everything is tested together; then, with your yes, staging → main (the locked final branch). Each department finishes on its own branch first.

Built: department branches → staging → main. Staging does two jobs — it's where the parts assemble and the branch that promotes. One join, one hop. Cost: while you're merging department #2, staging sits half-built until it goes green (main is never at risk — nothing promotes while red).

Spec: department branches → a separate project-integration branch (assemble + test there) → main. A clean quarantine that keeps staging untouched. Cost: an extra branch + an extra hop on every project, even small ones.

The difference in one line: one shared integration branch per repo (built) vs one fresh integration branch per project (spec).

I'd: keep direct-to-staging — for nearly every project staging already is the "all together, tested" branch, and main is protected regardless. Add the extra branch only for a project with long, messy integration.

③ The paperwork templates

📋

Leave light, or build the full templates?

Two moments work changes hands: the core team hands a new department its brief (IN), and a finished department hands work back (OUT). Today both are light — a plan slice going in, a "done, tests pass" message coming out.

The gap going IN: the light brief has the what (your plan slice) but not the connections — a dependency map (who you rely on, who relies on you) and the exact shapes (interfaces/schemas) you must consume and expose. Example: API-Integration must expose data shaped a certain way; Front-end consumes it. If that shape isn't handed over and agreed up front, Front-end guesses — and the mismatch shows up at integration, the worst place to find it.

The gap coming OUT: "done" carries no proof. A real report shows test results, each requirement met (traceability), what's still open, and how to integrate it.

What "full" costs: two markdown checklists — handoff-package.md and completion-package.md — labeled slots the planners/manager fill in. That's the whole change.

I'd: build both. These are the two riskiest seams — starting blind to a dependency, or finishing with no proof. Cheap fix, big safety. Of all your calls, the one I'd actually do.
