How the work flows 🗺️

from your idea all the way to shipped — the full, detailed path

Read it in words

💡 1. Your idea
You think up a new thing to build and bring it to the Manager yourself.
🗣️ 2. Pick the language(s)
Before any planning, the Manager suggests the best language(s) so the plan is optimal — and you two talk through your preferences and why.
🏷️ 3. Name the repo
The Manager asks what you want to call it (and offers ideas from your idea). You choose the name.
🛠️ 4. Research agent sets up the repo
The Manager tells the research agent to create it. Default: private · in tr3-org · staging + main branches · agents.md = the modularity rule CUSTOMISED to this language & project (not global) + the merging rules.
the merging rule (baked into the repo): 5/5 → auto-merge to staging (no approval) · 7 tries to hit 5/5 · the agent may split it · each split gets 7 · still stuck → YOU pick: merge as-is OR more loops.
🧠 5. Manager decides what the job needs
The MANAGER works out the tools, the tech, and every other requirement to build the idea — 'this is what we need to execute this job.' The research agent does NOT decide this.
🔎 6. Research prices those requirements
The Manager hands that list to the research agent, who researches only the COSTS and any RESTRICTIONS of it (e.g. API rate limits).
the Manager can push back: If something looks off, the Manager grills the research agent or sends it back to re-check.
💷 7. Manager reports back
The research agent pings the Manager when done. The Manager tells you the cost and confirms the repo is set up.
✋ 8. YOU approve → start the pipeline
Only after you OK the cost + setup does the idea go down to the planners.
your gate: Nothing reaches the planners until you approve the cost + setup.
📝 9. Planners make a draft
The two planners take the idea and turn it into a first draft.
🎯 10. Manager triggers a Plannotator goal
The Manager takes the draft into Plannotator.
🧾 11. Fact sheet #1 (in the browser)
You check the fact sheet in your browser and approve it.
✅ 12. Approve the goal → into Wayfinder
You approve the goal; the approved plan auto-loads into Wayfinder.
🗺️ 13. Wayfinder — build the map
You and the Manager work together in Wayfinder: the map, the specs, all the decisions.
two checks wrap Wayfinder: Fact-sheet + goal to get IN to Wayfinder; a second fact-sheet + goal to come OUT to the PRD.
🧾 14. Fact sheet #2
From what you decided in Wayfinder, a second fact sheet is made. You approve it.
✅ 15. Approve the goal → back to planners
You approve the second goal.
📚 16. Planners write the PRD
It goes back to the two planners, who turn it into the PRD (the real plan).
🦴 17. SDD skeleton
The bare bones of how to build it.
📖 18. Full SDD
The complete build instructions.
🎟️ 19. Feature tickets (job cards)
The plan is cut into small job cards; each maps exactly to where it fits the full SDD (its own micro-SDD).
who carries the papers: Only the Manager moves each paper desk to desk. Filed in the Herdr vault: PRD · SDD · Tickets.
🔴 20. Build each card: RED → GREEN → TIDY
Feature-Tickets writes a failing test = what 'done' looks like (RED). Green-Pass makes it pass (GREEN). Feature- Tickets tidies it (TIDY). Then the next card.
where the code goes: Real code goes into the product repo. A copy is filed beside each card as a backup.
📦 21. Bundle into PRs of 5
Finished cards go out in pull requests — max 5 each; leftovers get their own (8 → 5+3).
⭐ 22. Robot scores each PR out of 5
Greptile grades the code. 5/5 auto-merges to staging (no approval). Below 5/5 → see the side note.
if it doesn't score 5/5: Up to 7 tries → the agent may split it into smaller PRs (its own call) → each split gets its own 7 tries.
✋ then YOUR choice: A split still stuck after its 7 tries → you pick: (a) more loops, or (b) merge it as-is.
🧪 23. Testing gate
Once it's 5/5, ask 4 quick questions: needs testing? tested? scheduled? blocked by keys (API keys etc.)?
✋ 24. YOU approve → staging → main
Going live is a SEPARATE pull request. It needs a passing test AND your explicit yes. Never automatic.
📍 YOU ARE HERE → PR #6
PR #6 is exactly this final go-live yes: it ships the tested rules from staging to main, so every team gets them.

👥 Who talks to who

  • Chain: Agent → Manager → Ops → YOU. Your reply comes back down the same way.
  • Managers never message you directly — even decisions go through Ops.
  • An agent tells its Manager the instant a job is done — it never goes quiet.
  • Manager silent for 1 hour → the agent goes straight to Ops → Ops tells you.
  • "No change" is just logged; only real blockers, decisions, or questions reach you.
  • Every message starts with a label: "Sender -> Receiver:".
  • The Manager never trusts "done" on a word — checks the real commit, test count, and score.

🔁 Reports & the daily heartbeat

  • Work blocks: B1 09:00–13:00 · B2 14:00–17:00 · B3 18:00–20:00 (with breaks).
  • Each block: a Spaceship report (15 min before) and an End-of-block report — what's done and what can carry on without you.
  • Those block reports do NOT list PRs. A PR is named only if it is a real BLOCKER — work can't move until it's merged to staging, or the next stage strictly depends on it.
  • In-block blocker report: ad-hoc, only for such a hard blocker (including a must-merge PR).
  • END-OF-PHASE PR TABLE: you ALWAYS get this at the end of every phase — blocker or not — one row per PR + a bottom line.
  • Ops 30-min rule: waits for 2+ teams, then tells you; after 30 min quiet a team keeps going on pre-approved work — never idle; it returns the moment you reply.
  • Every pause writes a handoff note: commit + push, then branch, last commit, % done, next steps, blockers, last 3 handoffs (+ session IDs), chat links, watch-outs.
  • "Done" is graded, not trusted: the author writes the checklist, the Manager grades it; your only sign-off is ship-to-main.
  • Every decision to you carries 3 things: how big? · what else? · what if we don't? (+ an ELI5 link).

🎨 Who's who

  • YOU (Bobby) — the boss — has the ideas and gives the approvals
  • Ops — the messenger — carries messages between the Manager and you, and batches them
  • Manager — runs one team; the only one you talk to
  • Research agent — sets up the repo and researches the tools + their costs/limits
  • Planners / Writers — make the draft, then the PRD, then the SDD build instructions
  • Builders — Feature-Tickets writes tests + tidies; Green-Pass makes them pass
  • Greptile robot — scores each pull request out of 5
  • staging / main — staging = the practice stage; main = the live shelf every team builds from
