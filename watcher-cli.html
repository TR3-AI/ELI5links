The bug‑watcher 🔭🐛

one command — it catches the loud stuff and shows you where

idea — not built yet 🧰

You give it one command

The one you already use to run or test your code — cargo test, go test, or pytest.

⬇️
👀

It runs it and watches

You start it once: watcher -- cargo test. It runs your command and keeps an eye on it.

how it knows something broke

💥

A crash

The program dies or throws. Caught the moment it happens.

⬇️
✅

A failed test

A red test. That is a caught bug — and it knows which one.

⬇️
⏱️

A freeze

Nothing finishes in time. A timer notices the quiet and flags it as stuck.

what it does next

🔎

It grabs the clues

What you ran, the error, the exact test that failed, the input that broke it, and where it got stuck. Saved to a little file.

⬇️
🔬

It replays under the debugger

It runs the same thing again, slowly, under a magnifying glass — and stops at the exact broken spot so you can look.

one tool, three languages

🦀

Rust

Uses LLDB, Rust's debugger. Stops on the panic and shows the trail back to the line.

⬇️
🐹

Go

Uses Delve (dlv). Stops on the panic — and for a freeze it lists every stuck task so you see who's blocking.

⬇️
🐍

Python

Uses pdb (or debugpy). Drops you right on the line that broke, so you can poke around.

the honest bit

🤫

What it won't catch

Quiet wrong answers — code runs, the result's just off. Those still need a test or check that says what “right” is. The watcher jumps on crashes, red tests, and freezes — not silent wrongness.

🎯

The short version

One CLI, same steps for all three. Point it at your run or test command; it watches, catches a crash, a red test, or a freeze, saves the clues, then reopens the exact spot under Rust's, Go's, or Python's debugger.
