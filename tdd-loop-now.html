How our TDD loop works now 🔁

test first, clean as you go, checked twice

👥

Two workers, on purpose

Feature Tickets writes the test, cleans the code, and owns the pull request. Green Pass only makes the test pass. Different workers on purpose — you can't game a test you didn't write. The manager just watches and reports; it never touches code.

⬇️
1 🔴

RED — a failing test, first

The big design is cut into small tickets (each with a mini-spec). For each one, Feature Tickets writes an honest failing test before any code — it checks what goes in and comes out, not the private guts, and none of the cheat-tests.

⬇️
2 🟢

GREEN — make it really pass

Green Pass makes that test pass with the smallest change — and a real pass, not a fake one (no hard-coding the answer, no gaming it). Then it hands back.

⬇️
3 🧹

REFACTOR — tidy up now

Feature Tickets cleans the code against a fixed list of 12 "code smells" (duplicate code, mystery names, and the like). Cleanup #1 — right here in the loop. Steps 1–3 repeat for every ticket.

⬇️
4 🔍

CHECK IT TWICE

Before the pull request, Feature Tickets reviews its own work two ways: Clean? (the 12 smells again) and Right? (does exactly what the ticket asked, no more). Cleanup #2.

⬇️
5 🚦

THE GATE

Batch up to 5 tickets into a pull request. A robot reviewer (Greptile) scores it. 5/5 → auto-merges to staging. Stuck below 5/5? 7 tries → split it smaller → then it comes to you.

⬇️
6 🏁

ONLY YOU PROMOTE TO MAIN

Staging → main needs a passing test and your explicit yes. Nothing is ever self-merged.

Short version: test first → really pass → tidy vs 12 smells → check twice (clean + right) → robot gate → your yes to main. Cleanup happens both in the loop and at the gate; the test is honest from the first red.
