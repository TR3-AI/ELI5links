bug-watcher — straight answers ✅

what it actually does today — and what earlier pages oversold

You asked 6 things

📋

Here are the honest answers

Based on the real code, not the earlier pages. Where a page promised more than what's built, it's marked not built yet.

1 · does it get in your way?

🖥️

It's its own little program

You run bug-watcher in its own terminal or pane and leave it open. It watches your project folder and stays out of your editor. It never changes your files — unless you turn on --autofix. Stop it with Ctrl-C.

2 · what happens the moment you save

💾

It waits half a second

So a burst of saves counts as one. Default is 0.5s of quiet before it acts.

⬇️
🧹

It ignores the noise

Skips .git, target, node_modules, .venv, build folders, and its own findings.json. Keeps real files — even ones you deleted or renamed.

⬇️
🔄

It re-runs your checks, in order

cargo build, then cargo test. If the build fails, it skips the tests. Then it writes findings.json and prints green ✓ or a one-line summary.

3 · how it decides something's a bug

🚦

It reads facts, not meaning

It never understands your code. It runs the real commands and reads how they ended.

⬇️
🧾

The clear failures

Ran past a timer → freeze. Killed by a fatal signal → crash. Compiler errors → build broke. A test marked failed → test broke.

⬇️
✅

Green only when everything passes

If a check can't even run (bad setup, tool broke) or the result is unclear, that's never counted as green — and never auto-fixed.

⬇️
⚠️

A red mark isn't proof

It means a check failed — not that it found the cause. Code that runs fine but gives the wrong answer slips through, unless a test says what "right" is.

4 · the small fixes — where the know-how comes from

🔧

The language fixes its own small stuff

Not an AI. Not a debugger. It runs Rust's own fixers: cargo fix, cargo clippy --fix, cargo fmt.

⬇️
✂️

Small vs big = is there a ready, exact fix?

If the compiler or clippy hands over an exact, safe edit → small: it applies it and re-checks (capped at 5 rounds, only with --autofix). Anything else → big: it just writes the note and leaves it for you or the AI.

⬇️
📸

It fixes on a copy

Fixes run on a scratch copy, then write back a file only if you haven't touched it since. Saved again mid-fix? It skips that file and retries next save.

5 & 6 · the honest corrections

not built yet 🔦

No debugger — CodeLLDB is not used

Earlier pages said a debugger (CodeLLDB / Delve / pdb) peeks at crashes. That isn't built. "Crash" just means the process was killed by a signal; "freeze" just means it ran past the timer. No debugger runs.

⬇️
not built yet 🛑

"A new save cancels the old check" — not real

Checks run one at a time. A new save can't interrupt one already running. The "cancelled" label exists in the code but nothing triggers it yet.

⬇️
not built yet 🦀

Rust only, so far

Only the Rust (cargo) adapter is built. Python and Go (ruff, gofmt, Delve, pdb) are ideas, not code.

⬇️
🔀

"expected vs got" can look backwards

For assert_eq!(actual, expected) it labels them by position — so your actual value can show up under "expected". Small, worth fixing.

⬇️
not tested yet 🧪

Only the run-once mode is tested

The one-shot --once run is smoke-tested. The live "keep watching" loop is written but not yet exercised end to end.

🎯

The short version

It's a separate little program you leave running. On save it re-runs cargo build + cargo test, reads the result, and tells real failures from tool noise. Small, exact fixes it applies with Rust's own tools; everything else becomes a note. No AI, no debugger — and today it's Rust-only, with the live watch loop still untested.
