Q1 · does it get in your way?

Q1 🖥️

Its own little program, off to the side

You run bug-watcher in its own terminal or pane and leave it open. It watches your project folder and stays out of your editor. It never changes your source files unless you add --autofix — but it always writes its own findings.json report. Ctrl-C stops it.

Q2 · what happens the moment you save?

Q2 💾

It waits half a second

So a burst of saves counts as one. Default is 0.5s of quiet before it acts.

⬇️
🧹

It ignores the noise

Skips .git, target, node_modules, .venv, build folders, and its own findings.json. Keeps real files — even ones you deleted or renamed.

⬇️
🔄

It re-runs your checks, in order

cargo build, then cargo test. If the build fails, it skips the tests.

⬇️
📝

Then it settles — and writes the report

Without --autofix it writes right away. With it, if a build issue is fixable, it runs the fixer batch, re-checks, and loops — up to 5 rounds — and only when it settles (or hits the cap) does it write findings.json and print green ✓ or a one-line summary.

Q3 · where do the small fixes come from?

Q3 🔧

From the language's own tools — not an AI, not CodeLLDB

It runs Rust's own fixers: cargo fix, cargo clippy --fix, cargo fmt. It has no fix ideas of its own — a compiler suggestion is only what switches the fixers on (exact rule in Q6).

Q4 · what is CodeLLDB's role?

Q4 🔦

Today: none — no debugger is wired in

Earlier pages saying CodeLLDB peeks at crashes were wrong. "Crash" just means the program was killed by a signal; "freeze" just means it ran past the timer — both read from how the process ended, no debugger involved.

⬇️
planned — not built yet 🔍

If it's added later: a magnifying glass, nothing more

The plan is best-effort and only after a crash or freeze, purely to add detail (like a stack trace). It would never decide whether something's a bug, and never auto-fix.

Q5 · how does it decide bug vs error vs failure?

Q5 🚦

It reads facts, not meaning

It never understands your code. It runs the real commands and reads how they ended.

⬇️
🧾

The clear failures

Ran past a timer → freeze. Killed by a fatal signal → crash. Compiler errors → build broke. A test marked failed → test broke.

⬇️
✅

Green only when everything passes

If a check can't even run (bad setup, tool broke) or the result is unclear, that's never counted as green — and never auto-fixed. (But heads up: those results can still leave findings.json empty — see the gaps below.)

⬇️
⚠️

A red mark isn't proof

It means a check failed — not that it found the cause. And code that runs fine but gives the wrong answer slips through completely, unless a test says what "right" is.

Q6 · small bug vs big bug — the rule

Q6 ✂️

The exact rule: is there a fixer trigger?

Auto-fixable = at least one build (compiler) diagnostic carries a suggested replacement. That — and only that — switches on the full three-command batch (cargo fix + cargo clippy --fix + cargo fmt), which re-checks after, capped at 5 rounds and only with --autofix. Big / not eligible = no such trigger: test fails, crashes, freezes, and build errors with no suggested edit → note only, never auto-fixed. (That trigger is too broad — see below.)

⬇️
📸

And it fixes on a copy

Fixes run on a scratch copy, then write back a file only if you haven't touched it since. Saved again mid-fix? It skips that file and retries next save.

the honest corrections

not built yet 🛑

"A new save cancels the old check" — not real

Checks run one at a time. A new save can't interrupt one already running. The "cancelled" label exists in the code but nothing triggers it yet.

⬇️
known gap 📋

A tool/setup failure may leave no note

When a check can't even run (bad setup, a broken tool) or the result is unclassified, it's shown on screen and never counted green — but findings.json can still come out empty. Should always leave a note.

⬇️
known gap 🧹

The auto-fix trigger is too broad

If any diagnostic comes with a suggested replacement — even a "might be wrong" one — it triggers the whole fixer batch: cargo fix, cargo clippy --fix, and cargo fmt. Those then make their own edits across the project (reformatting, unrelated lint fixes) — not just that one spot.

⬇️
not built yet 🦀

Rust only, so far

Only the Rust (cargo) adapter is built. Python and Go (ruff, gofmt, Delve, pdb) are ideas, not code.

⬇️
known gap 🔀

"expected vs got" can look backwards

For assert_eq!(actual, expected) it labels them by position — so your actual value can show up under "expected". Small, worth fixing.

⬇️
not tested yet 🧪

Only the run-once mode is tested

The one-shot --once run is smoke-tested. The live "keep watching" loop is written but not yet exercised end to end.

🎯

The short version

It's a separate little program you leave running. On save it re-runs cargo build + cargo test, reads the result, and tries to sort real check failures from tool/setup noise. A recognized failure becomes a note in findings.json; small ones with a ready compiler fix it can apply. No AI, no debugger, Rust-only — and a red mark is a failed check, not proof of a bug.
