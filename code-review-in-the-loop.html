Who actually does the code review? 🔍

new review rules — and which teammate they land on

1 🔍

I borrowed a proven method

There's a well-known code-review method by Matt Pocock. I took the parts that fit us and left the parts that don't (it spins up extra helper bots — our manager isn't allowed to). Then I wired the good parts into how the team builds.

⬇️
2 ⚖️

Rule 1 — check every change two ways

Clean? — measured against a fixed list of 12 known "code smells" (duplicate code, mystery names, and the like). Right? — does it do exactly what the ticket asked, no more, no less. A change can pass one and fail the other, so both get reported.

⬇️
3 🧪

Rule 2 — honest tests

Tests must prove the code really works, not fake a pass. No test that just repeats the code, no peeking at the insides, and no test that breaks the moment you tidy up.

⬇️
4 🤷

The catch you spotted

A rule everyone can see is nobody's job. My first pass put the rules where all 10 seats read them as background — but told no worker "this one's on you." You caught that.

⬇️
5 👷

So I handed it to the workers

Feature Tickets now owns it: write honest tests, clean the code against the 12 smells, and double-check its own work before the pull request. Green Pass gets one rule: make it really pass — no faking.

⬇️
