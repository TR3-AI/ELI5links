Clean code isn't the same as right 🎯

Tidy tools make code neat. They can't prove it does the right thing. Here's how we get closer.

🧹

The gap

fmt tidies your code; clippy nitpicks it. Both make it cleaner. Neither proves it's correct — and clippy sometimes cries wolf, flagging things that are actually fine.

⬇️
🧪

Fix 1 · stronger tests

The watcher only knows by running your tests, so "green" is only as good as they are. The trick isn't more lines touched — it's tests that would truly fail if the behavior broke. Then lock the separate judge-tests so the AI can't water them down. (Its own tests stay free to change.)

Fix 2 · a reviewer that reads the change

A smart model reads what changed against what you asked for: does it meet the ask? skip a case? any logic or security hole? A tidier can't do that. It adds evidence — it still can't promise "correct."

⬇️
🧱

Fix 3 · stack different checks

Build + tests (built), clippy, a scan for bad dependencies, and the debugger for crashes/freezes (planned). Each catches a different miss; together they shrink the blind spot. No single one means "correct."

⬇️
🚪

Fix 4 · say what you actually checked

Three answers, not two: pass / fail / couldn't-check. "Green" only ever means "the checks we have passed" — never "this is correct."

Taming clippy's crying wolf

Don't fail on every warning. Pick the serious ones to fail on; show the rest as notes. That keeps the signal worth trusting, instead of something people learn to ignore.

🎯

The short version

clippy + fmt clear the cheap mess; strong tests + the reviewer move you from clean toward right. You're shrinking the blind spot, not erasing it — no tool can prove "correct."
