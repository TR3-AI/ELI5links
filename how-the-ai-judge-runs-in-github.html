How the AI judge runs in GitHub ⚖️

it doesn't live there — it gets a phone call

1 🤖

GitHub has a built-in robot

It's called Actions. When a pull request opens, GitHub automatically spins up a fresh, clean cloud computer and runs a job on it. That's “the cloud” — a throwaway machine GitHub owns.

⬇️
2 ⚙️

Rules check first (R1)

That job runs the no-AI checks first: the locked tests, the tamper check, clippy + fmt. Only if those pass does the AI judge run.

⬇️
3 📞

The judge is a phone call

The AI doesn't live in GitHub. The job runs a small program that phones an AI over the internet (an API call) and asks it to judge.

⬇️
4 📤

What it sends over

The exact change (the diff), what you asked for (the approved spec), and the rules-check report. The question: does this meet intent? any logic or security holes? were the tests weakened?

⬇️
5 🔑

The key is in a locked drawer

The AI's key sits in GitHub's encrypted Secrets, readable only by the job on GitHub's machine. The coding AI on your laptop never sees it — can't run the judge, can't fake its answer.

⬇️
6 🛡️

It can't be tricked by hidden notes

It reads the change with code comments stripped out for the verdict, so the coder can't hide “just pass me” in a comment. A FAIL must carry real evidence — the rule, the spec line, and the file + line.

⬇️
7 🚦

The verdict blocks the merge

The job reports pass / fail back to the pull request as a required check. Red = GitHub itself won't let it merge.

✅

In one breath

GitHub's robot runs on a clean cloud machine, phones a separate AI with the change + the spec, and posts a verdict the coder can't reach or fake — because the key stays locked in GitHub.
