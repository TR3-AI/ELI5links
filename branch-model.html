How code gets to main 🚦

ticket → your team's branch → staging → main — one look, then decide

🗺️

Three steps, that's the whole thing

your team's branch → staging → main. Each team fixes on its own branch (api, data, core). Finished work goes to the one staging. Staging goes to main with your OK. Everything below is just the detail.

⬇️
1 🎫

Tickets land on your team's branch

Work is batched 5 tickets per PR (kept). Greptile scores it. 5/5 → auto-merge into that team's own branch. Your normal loop — just on the team branch, not the shared one, so teams never clash.

⬇️
2 ✂️

Below 5/5? Same rule as today

7 tries to reach 5/5. Still short → the feature-ticket agent splits the PR; each split gets its own 7 tries. Anything still stuck comes to you: (1) merge below 5/5, or (2) allow more tries.

⬇️
3 🧪

Every 5/5 gets the 4 test questions

The moment a PR hits 5/5 on the team branch, we ask the 4 testing questions (needs testing? done? scheduled? blocked on keys?) — right there, per team. Same rule you have now.

⬇️
4 🤝

Finished team → staging

When a team is fully green (all tickets in, its tests pass), its branch PRs into the one staging. Staging only ever gets whole, finished teams — never half-done. No collisions.

⬇️
5 🧩

Staging runs the big test

On staging we put all finished teams + the codebase together and test the whole thing. This is the "passing test" your rules already require before main. No second Greptile here — that job's done on the team branch.

⬇️
6 🏁

Staging → main — unchanged

Whole-system green → main, with your approval. Exactly like today. Short names: api · data · core → staging → main, plus a tiny DEPARTMENTS.md saying which branch is which.
