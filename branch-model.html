Decision 5: how the code is organised 🌿

one repo, one branch per team, a ladder up to main — nothing ever deleted

1 📦

Everything lives in one repo

No separate repo per team. One project repo, and each department gets its own branch inside it. That's why a department's research agent never spins up a new repo — it's all the same one, just different branches.

⬇️
2 📂

Each team works in its own "worktree"

A worktree = a separate working copy of the repo on disk, checked out to its own branch. So teams (and individual tickets) build at the same time without stepping on each other. Each department gets a worktree; each ticket gets one too.

⬇️
3 🪜

Branches roll upward, like a ladder

ticket → department → project → main. Small pieces merge into their department; departments merge into one project branch; that goes to main. Example:
feat/typeless/api/api-004
→ department/typeless-api
→ project/typeless-integration
→ main.

⬇️
4 🏛️

The core team gets a branch too

Since the core team also builds its own section, it has its own department branch just like the rest (e.g. department/typeless-core). It's a team on the ladder, not above it — and it also does the final glue-together into project + main.

⬇️
5 💾

Closing a team never deletes its work

When a department finishes and you say close, only the panes close. The branch, commits, PRs, and chat history all stay — forever. Because teams run in waves of max 3 at a time, finished branches just sit there, safe, as the permanent record of what that team did.

⬇️
6 🗺️

Anyone can see what each branch is for

Clear names plus a written department map in the repo say which branch is which department, what it owns, and how it connects back to the core team and main. Open the repo and the whole shape is obvious — no guessing.

The 3 calls inside decision 5 👇

🔀

A. New integration branch, or keep "staging"?

Signing up for: the one place all departments meet before main. Deciding: make project/<proj>-integration that meet-up branch (the new "staging"), or keep today's plain staging? Result: one clearly-named place per project vs. the generic one we use now. My pick: use project-integration as the new staging — the name tells you the project and stops two projects sharing one staging.

🛡️

B. Where do the checks happen?

Signing up for: the quality gates on the ladder. Deciding: keep Greptile 5-of-5 on every PR into a department branch, and your approval only at the final push to main? Result: departments self-check as they build; you only sign off the final merge. My pick: yes — same gates as today, just applied per department, your OK stays the gate to main.

🏷️

C. How we label a team's purpose

Signing up for: making the repo self-explaining (your new requirement). Deciding: a short DEPARTMENTS.md map the manager keeps current, plus a one-line purpose on each department branch/PR? Result: anyone opening the repo sees every team, its section, and its link to the core team. My pick: yes — a tiny map file plus branch/PR descriptions; cheap, and it kills confusion later.

Short version: one repo, one branch per team, a ladder up to main, nothing ever deleted. Say yes to A, B, C (or tweak) and decision 5 is locked.
