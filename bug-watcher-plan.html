bug-watcher — the plan 📋

what's built, what's missing, how it finds bugs, and the exact order we fix it — in plain words

🎯

The one goal

Check the AI's work every time code is saved, instead of trusting it at the end. Judge it by the compiler and the tests (things that are hard to fake), then force it to fix what it broke before it's allowed to finish. Catch trouble early, not in review or production.

Part 1 · how it actually finds a bug

🔎

Does it copy your code? No.

It runs your real project, in place. After a save it runs the real cargo build, then the real cargo test — on your actual files. No copy, no sandbox clone.

⬇️
📖

It reads facts, not vibes

Won't compile → build broke. A test reports FAILED → test broke. Runs past a time limit (build 180s / test 300s) → freeze. Killed by a fatal signal → crash.

⬇️
🧾

Each problem becomes a "finding"

A finding always has a plain message. It gets a file + line only when the compiler hands one over. It gets expected-vs-got only from a failed assert_eq! — and today that pair is often backwards (a known bug). It does not run twice to confirm — one run per save.

⬇️
⚖️

As sharp as your tests — no sharper

"Found" means the compiler or the test runner said so, or it hung, or it crashed. If nothing tests a behaviour, it can't see it.

Part 2 · where the receipt goes

🗁️

findings.json is just a file

It writes a file named findings.json in the folder you launched it from (not the project folder), unless you pass --findings. Clean run = an empty list [].

⬇️
🤖

Nobody hands it to the AI (yet)

The file is not given to the AI and not dropped into the chat. The terminal only prints a count and the path. For the AI to see the real details, something has to open and read that file — and nothing does that automatically today. This missing step is called "deliver."

Part 3 · what's built & working

built ✅

A real Rust v1

A working command-line tool that builds and has its own tests. This part is real, not a sketch.

⬇️
built 👀

Watches & runs the real checks

Watches your folder, ignores noise (.git, target, node_modules…), waits ~0.5s so a burst of saves counts as one, then runs the real build and test (and skips the test if the build fails).

⬇️
built 🛡️

Runs commands safely

Each check runs in its own process group, gets its whole tree killed on timeout, can't deadlock on output, and records exit code / signal / timed-out.

⬇️
built 🏷️

Labels the result honestly

Pass / real code failure / tool-or-environment failure / unknown. (There's a "cancelled" label in the code too, but nothing ever produces it — treat cancel as not built.)

⬇️
⚠️

Crash & freeze are best-effort

Crash only fires if cargo itself is signal-killed — a crashing test usually makes cargo exit 101, so it can slip through with no finding. Freeze = any timeout, so a slow-but-fine build gets flagged too. Ordinary test failures are caught fine.

⬇️
built 🧾

Writes the receipt

It writes findings.json on each completed check. Caveat: if it can't launch cargo or the write itself fails, that round writes nothing and an old receipt can be left stale.

⬇️
built 🔧

Optional --autofix (experimental)

Applies the compiler's own fixers (cargo fix / clippy --fix / fmt), then re-checks, up to 5 rounds. The write-back is race-guarded (works on a temp copy, only writes files whose hash didn't change) — but the fixers themselves run unbounded (no timeout, no tree-kill) and silently (errors and output are ignored). Treat it as experimental.

Part 4 · what's missing (the gaps)

to build 📮

1. Deliver

Nothing puts the findings in front of the AI. It's just a file sitting on disk.

⬇️
to build 🚦

2. Enforce — the exit code can't catch a red

Every failure it detects, and "no project found", all exit 0. It only exits non-zero on an internal plumbing error — and in watch mode even that is swallowed. So no gate, CI step, or && can catch a red today.

⬇️
to build 🎓

3. The catch — grading its own homework

If the same AI can weaken a test, change an expected value, or edit the watcher's config, then "green" means nothing. Nothing protects the tests/gate/config today.

⬇️
bug 🔀

Expected vs got is often backwards

The assert_eq! reader blindly maps left→expected and right→got, so the receipt can show them reversed.

⬇️
bug 📭

A red can be empty or stale

A tool/env failure writes an empty []; and an error before the write leaves the old file — which can even still read "green" from an earlier run.

⬇️
bug ⏱️

No cancellation

A new save doesn't cancel the check already running, so on fast saves it can be grading stale code.

⬇️
bug 🧹

Auto-fix is eager, heavy & unbounded

One fixable hint runs all three fixers across the whole project after copying the entire tree to a temp folder. And each fixer runs outside the safe runner — no timeout, no tree-kill — with its errors and output thrown away. So a stuck or broken fixer can hang or fail silently.

⬇️
scope 🦀

Only Rust — and thin tests

No other languages yet. The live watch loop has no real test and there's no end-to-end test. The CodeLLDB debugger help for crashes/freezes is planned, not built.

Part 5 · the fix plan (in order)

📊

Step 0: measure it first

Before building more, prove the accuracy. Run a set of fixtures — clean, build-fail, test-fail, crash, timeout, tool-missing, and rapid-save — and count catches, misses, false alarms, and how fast it reacts. That turns "should be reliable" into a real number.

⬇️
🥇

First: make red bite

1) Make --once exit non-zero on a real failure — that's the mode a gate or CI uses (watch mode stays alive, so it has no exit to gate). 2) Always leave a real receipt, so a red is never empty or stale.

⬇️
📬

Then: deliver & enforce

3) Deliver — the checker returns one report in memory (a clear status + the findings). A --json mode prints that report to the screen for the wrapper or per-edit hook (OMP / Claude Code) to read directly — it never re-opens the receipt file, so the stale/empty race can't come back; the same report is also saved to disk atomically. 4) Enforce — --once turns that status into a non-zero exit, and while red we block the finish / commit / next-task but keep Edit/Write open so it can fix.

⬇️
🔒

Then: lock the graders

5) Protect the test / gate / config paths so the coding AI can't touch them; acceptance tests owned by you or an independent agent. Green only counts if the grader wasn't edited.

⬇️
🧰

Then: clean up & grow

6) Fix the expected/got swap and make auto-fix trustworthy: run the fixers through the timeout-guarded runner, stop swallowing their errors, and narrow which fixer and files run — while keeping the temp-copy + hash guard that stops it clobbering your saves. 7) Prove the watch loop with a real test and add cancellation on new save. 8) Add more languages, each bringing its own tests.

Part 6 · how accurate is it?

🎯

Expected strongest — but not proven

Build breaks and ordinary test failures should be the surest catches. But it's not measured end-to-end yet: there's no live-loop test, flaky tests aren't deterministic, and with no cancellation a queued save can break the "right after this save" link. Strong on paper, unproven in practice.

⬇️
🌫️

Best-effort (can be wrong)

Crashes (only if the top command is signal-killed) and freezes (any timeout, including a slow-but-fine build). These can false-alarm or miss.

⬇️
🕳️

Blind

Anything with no test, or output that's wrong but still compiles and passes. And until cancellation exists, it can grade stale code. Net: it catches problems earlier, but only the kinds your compiler and tests already cover.

Part 7 · the big caution

🚧

"Green" is not "correct"

Green only means "the checks that exist passed" — not that the code is right. It's weak until the graders are locked, and the stale-receipt bug can even show green on broken code. Don't read green as "done."

🎯

The short version

The detector is real — a Rust v1 that catches loud bugs on save and writes a receipt. The missing heart is deliver + enforce: make red exit non-zero (in --once), always leave a receipt, hand the findings to the AI, and block the finish — not the edits — until it's green, with the tests/gate locked so it can't grade its own homework. Then the AI is checked as it goes, not trusted at the end.
