The reviewer, the debugger & the AI judge ⚖️

the plan — and what’s real today

1
📦

Only 1 of 3 is actually built

Three pieces are meant to stack. Only the first exists: the watcher (it builds + tests your code on every save). The reviewer, the AI judge inside it, and the debugger are all planned, not built yet — and the watcher still has 11 known bugs to fix.

⬇️
2
🔎

The reviewer: the honesty check

A green build + green tests don’t prove the change is right or honest. At commit / PR time the reviewer reads the actual change against what you asked for. It comes in two halves — a mechanical gate and an AI judge. (Planned.)

⬇️
3
🔒

Half 1 — the mechanical gate

No AI, no API key, no cost. It re-runs the protected tests and checks the coding AI didn’t quietly weaken its own graders (the locked tests + config) to fake a pass. Just rules — nothing leaves your machine.

⬇️
4
🤖

Half 2 — the AI judge

A strong model (Opus-class) reads the change: does it meet what you asked? did it weaken the tests? any obvious logic or security holes? It costs tokens, so it runs only at commit / PR time, not on every save.

⬇️
5
🧠

Two different AIs — don’t mix them

The coding AI writes the code and gets handed the findings. The reviewer’s AI judge grades that work. And the watcher itself is not an AI — it’s just the compiler and the test runner, which are the hardest things to fake.

⬇️
6
🚪

The verdict: PASS / FAIL / BLOCKED

PASS — all green and the graders untouched. FAIL — a real code break, or the AI edited a locked grader; only FAIL says “your code is wrong.” BLOCKED — couldn’t verify (a timeout, a crash we can’t pin, or the judge is unsure). It still stops the ship, but never blames the AI.

⬇️
7
🐛

The debugger: where did it break

When the watcher flags a crash or a freeze, the debugger replays it under CodeLLDB (the Rust debugger; plain LLDB is only the backup), reads the top of the stack, and gives a plain “likely here, likely why.” It’s advisory only — it never changes the score. (Planned.)

⬇️
8
🧩

How they fit together

One wrapper runs the show: the watcher on every save → the reviewer at commit / PR → the debugger only on a crash or freeze. They pass simple hand-offs, nothing nested — so each can be built and tested on its own.

⬇️
9
📋

The order — and what’s next

Build order: finish the watcher first (hand over its findings + block a bad save), then the reviewer (gate, then judge), then the debugger. Next up: rework PR #1 (fix the 11 bugs), add clippy + fmt to the gate, then add the judge. Waiting on your yes to the one goal.

Short version: only the watcher is built (11 bugs to fix). The reviewer, its AI judge, and the debugger are the plan — a mechanical gate + a strong-model judge at PR time, plus a CodeLLDB replay on a crash. The verdict is always PASS / FAIL / BLOCKED, and “couldn’t verify” never blames the AI.
